# Постоянная синхронизация Phantom: GitHub → Windows → AEZA

Актуально: 11.11.2026. Согласованная схема для тестового сайта МДИС «Фантом».

## Источник истины
- **GitHub**: репозиторий `Mixerland1/phantom-product-audit`, ветка `main`; изменения вносятся здесь.
- **Локальный проект**: `F:\MVP\phantom website`. Эталонный HTML на GitHub имеет имена `index.html`, `phantom-home.html` и имена отраслевых/продуктовых страниц без номерного префикса. Локальная папка `макеты` сохраняет привычные соответствия `02_...`–`11_...`.
- **Тестовый AEZA**: только `/srv/mdis-preview/site`, URL `https://relay.mixerland.ru:8443/mdis-preview/`. Production `mdis.ru` не затрагивается.

## Однокнопочный обновлятор
После однократной установки локальный код находится в `F:\MVP\phantom website\tools\phantom_sync.py`. Ярлык «Обновить Phantom» запускает этот инструмент на Windows. Исходный установочный пакет хранить в проекте или в текущей беседе; рабочий код находится в локальной папке, а не исполняется прямо из GitHub.

Инструмент запрашивает текущий SHA ветки `main`, получает полное дерево GitHub, выбирает новые/изменённые корневые HTML (кроме исторических номерных дублей), все поддерживаемые ресурсы `assets/**` и `*.md`. Используются **закреплённый SHA коммита**, проверка Git blob SHA-1 и SHA-256.

Порядок: скачать → проверить HTML/`noindex`/ссылки/целостность → проверить конфликты с локальными изменениями → сохранить резервные копии → синхронизировать `макеты`, пакет предпросмотра и документы → через SSH сравнить SHA-256 файлов AEZA → загрузить отсутствующие или отличающиеся ресурсы архивом во временную папку → проверить stage SHA-256 → сделать серверную резервную копию → заменить только изменившиеся файлы → сверить серверные SHA-256 → проверить обычные HTTP URL без `?v=` и записать итог.

**Если серверные файлы совпадают, загрузка не выполняется, но HTTP-проверка всё равно проводится.** Это устраняет ложную ошибку прежнего конвейера на новой главной. Удалённые в GitHub файлы автоматически не удаляются с AEZA.

## Документы
- GitHub Markdown синхронизируется локально; `AGENTS.md` и `PHANTOM_HOME_README.md` идут в корень проекта. Другие Markdown — в `документация\Из_GitHub`, если нет специального соответствия.
- **Нельзя затирать исторические локальные `STATUS.md`, `HANDOFF.md`, `README_проекта.md` и `документация\28_Итоги_сессии_11-11-2026.md`.** Они остаются на компьютере без полной замены; в первые три добавляется только ссылка на текущий статус.
- Актуальный машинный статус хранится в `документация\СОСТОЯНИЕ_СИНХРОНИЗАЦИИ_PHANTOM.md`. Старое состояние не выдаётся за успешную публикацию.
- `публикация\_phantom_sync_state.json` фиксирует прошлые хэши локальных копий. Самостоятельные локальные правки после синхронизации вызывают конфликт, а не незаметно перезаписываются.
- Резервные копии Windows — `публикация\_backup_sync`; серверные — `/srv/mdis-preview/site/.backups/`.

## Важные границы
1. Это **односторонняя** доставка GitHub → Windows → AEZA, а не двусторонняя синхронизация. Локальные изменения в GitHub автоматически не отправляются.
2. На AEZA размещать только сайт и ресурсы, **не публиковать Markdown, инструменты или данные проекта**.
3. Если имя нового HTML не имеет номерного префикса и в нём настроен `noindex, nofollow`, обновлятор автоматически включит страницу. Исторические `06_...`–`09_...` в корне GitHub не выкладываются и не переопределяют актуальные имена.
4. SSH выполняется только к тестовому AEZA: прямое соединение или Jump Host через relay. Конфигурация доменов, Nginx/VPN/production не меняется.
5. Не считать процесс успешным без HTTP 200 и совпадающих SHA-256. В случае ошибки локальная папка может уже содержать новую версию, но статус публикации остаётся непроверенным.
6. Обновлятор намеренно не перезаписывает собственный код при появлении нового файла в GitHub. Обновление программного механизма — отдельная проверяемая установка.

## Работа в будущих сессиях
После изменения HTML/CSS/JS/картинок и Markdown в GitHub сообщить пользователю: **«Готово в GitHub. Нажми “Обновить Phantom” на рабочем столе».** Обещать готовую публикацию только после успешного вывода программы. Нельзя делать новые одноразовые скрипты на каждую страницу, если задача укладывается в этот процесс.
