# Промпт для Codex: создать страницу услуги «Персональные решения» для сайта Phantom / МДИС

Ты работаешь в репозитории:

`Mixerland1/phantom-product-audit`

Базовая ветка проекта: `main`.

## Режим параллельной разработки — обязательно

Этот промпт выполняет **page-agent** в отдельной ветке/worktree. `main` — только базовая ветка.

### Владение файлами

Page-agent может создавать и менять только:
- целевую страницу этого промпта;
- уникальные assets, используемые только этой страницей;
- локальные стили этой страницы, если они необходимы.

Page-agent может читать, но **не должен изменять**:
- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- `docs/PHANTOM_SYNC_WORKFLOW.md`;
- общие CSS/JS;
- страницы других параллельных задач.

Если ниже по промпту требуется изменить общий файл, считать это **требованием для Integrator**. Не выполнять такую правку в page-ветке; перечислить её в финальном `Integration manifest`.

### Актуальность

Статические примеры общего header, `solutionPages`, порядка соседних страниц и других общих компонентов в этом промпте могли устареть. Не откатывать актуальный проект ради совпадения с примером. Текущее состояние базового `main` и правила `prompts/README.md` имеют приоритет для интеграции.

### Git и публикация

- Зафиксировать базовый commit SHA.
- Не коммитить напрямую в `main`.
- Не сливать свою ветку в `main`.
- Не публиковать на AEZA.
- Не менять production `mdis.ru`.

### Финальный отчёт

Помимо обычного отчёта промпта обязательно добавить `Integration manifest`: созданные page-owned файлы, необходимые изменения общих файлов, зависимости, выполненные и невыполненные проверки.

# 5. Что означает «персональное решение»

На новой странице раскрыть понятие через конкретные инженерные ситуации.

Персональное решение может потребоваться, когда:

- используется нестандартная или редко встречающаяся АТС;
- тип линий или протокол подключения не закрывается готовой конфигурацией;
- нужно объединить запись нескольких типов связи;
- требуется интеграция с внешней информационной системой;
- есть специфические требования к метаданным вызова;
- требуется особая архитектура централизованной или распределённой записи;
- необходимо адаптировать интерфейс или workflow работы с записями;
- нужен новый интеграционный модуль;
- стандартная линейка оборудования не соответствует условиям размещения или эксплуатации.

Каждый такой пункт должен быть сформулирован как **возможный предмет инженерного анализа**, а не гарантированная готовая функция.

Не обещать, что МДИС обязательно реализует любой запрос.

# 34. Критерий готовности

Работа считается выполненной, если:

- создан `personal-solutions.html`;
- услуга объяснена как инженерная адаптация/разработка в области систем записи;
- нет обещания «сделаем что угодно»;
- ясно показана граница стандартной конфигурации и индивидуальной разработки;
- есть понятный процесс от исходных данных до решения;
- история разработок МДИС используется как доказательство компетенции, но не как текущий compatibility list;
- показаны современные примеры SIPREC, ASR и monitoring;
- персональная разработка отделена от модернизации и обучения;
- в header появился раздел `Услуги`;
- `Персональные решения` ведут локально;
- модернизация и обучение временно остаются внешними, если ещё не перенесены;
- production `mdis.ru` не затронут.
