# 4. Главный принцип страницы

Не выдёргивать красивые цитаты из писем без контекста.

Каждая карточка должна содержать:

- организацию;
- дату письма;
- тип документа;
- краткую фактическую выжимку;
- ссылку/preview на оригинальный документ;
- при необходимости — точный масштаб эксплуатации, если он прямо указан в письме.

Не превращать письмо в рекламный slogan.

---

# 5. Не использовать слово «отзыв» шире источника

Письма могут иметь разный официальный характер:

- информационная справка;
- ответ на запрос МДИС;
- письмо об опыте эксплуатации;
- письмо о технической поддержке.

Поэтому на карточке полезно писать:

```text
Официальное письмо
```

или:

```text
Письмо об опыте эксплуатации
```

а не автоматически:

```text
Отзыв
```

если сам документ так не называется.

# 9. Не придумывать одинаковую конфигурацию

Даже если несколько филиалов ПАО «Россети» используют Phantom:

не писать:

```text

```

или:

```text

```

если письма этого не подтверждают.

У каждого объекта могут отличаться:

- версия ПО;
- аппаратная платформа;
- количество каналов;
- тип АТС;
- диспетчерская инфраструктура;
- схема резервирования.

# 17. Короткие выжимки должны быть нейтральными

Хороший формат:

```text
Филиал сообщает об эксплуатации МЦКРС «Фантом» и положительно оценивает взаимодействие со службой технической поддержки МДИС.
```

Только если это действительно следует из письма.

Плохой формат:

```text
Россети подтверждают абсолютную надёжность Phantom
```

# 18. Цитаты

По умолчанию **не использовать длинные прямые цитаты**.

Если в документе есть одна действительно полезная формулировка:

- максимум 1 короткая цитата;
- рядом организация и дата;
- обязательно ссылка на оригинал.

Не использовать testimonial quote без источника.

---

# 19. Подписи и должности

Если документ подписан конкретным человеком:

можно показать:

```text
должность
```

только если она читается и подтверждается оригиналом.

Не копировать:

- подпись;
- факсимиле;
- рукописные пометки;
- служебные номера телефонов;

в виде отдельных элементов страницы.

---

# 20. Персональные данные

Не извлекать и не акцентировать:

- личные мобильные номера;
- внутренние добавочные номера;
- email конкретных сотрудников;
- рукописные подписи.

Показывать только то, что необходимо для идентификации официального документа:

- организация;
- должность подписанта — при необходимости;
- дата;
- номер письма — если нужен.


# 33. Визуальное оформление

Страница должна выглядеть как **documented customer evidence page**.

Использовать:

- общий header;
- общий footer;
- hero rhythm;
- document cards;
- аккуратные preview писем;
- дату;
- организацию;
- 1–2 подтверждённых факта;
- light/dark.

Не использовать:

- звёздочный рейтинг;
- Trustpilot-like UI;
- fake avatars;
- stock portraits;
- огромные кавычки;
- логотипы как единственное содержание.

---

# 34. Что не делать

Не:

- менять production `mdis.ru`;
- придумывать содержание письма;
- придумывать рекомендации;
- придумывать количество объектов;
- смешивать данные разных источников без маркировки;
- считать все конфигурации одинаковыми;
- считать письмо 2024 года доказательством текущей версии системы в 2026;
- копировать личные контакты подписантов;
- копировать подписи;
- создавать рейтинг;
- создавать fake quotes;
- писать `100% довольны`;
- писать `лучшее решение`;
- использовать выражение `реальное оборудование`.

# 36. Техническая проверка

После изменений:

1. Проверить `reviews.html`.
2. Проверить один H1.
3. Проверить H1 → H2 → H3.
4. Проверить `noindex, nofollow`.
5. Проверить общий header.
6. Проверить общий footer.
7. Проверить light/dark.
8. Проверить актуальное число писем.
9. Проверить каждый оригинальный документ.
10. Проверить дату каждого письма.
11. Проверить точное название каждого филиала.
12. Проверить выжимку каждой карточки по оригиналу.
13. Проверить preview / внешнюю ссылку каждого документа.
14. Проверить `clients.html`.
15. Проверить `electroenergetika.html`.
16. Проверить `support.html`, если используется.
17. Проверить отсутствие личных контактов/подписей.
18. Проверить отсутствие битых ссылок.
19. Проверить отсутствие случайного перехода на `/`.
20. Проверить отсутствие horizontal overflow.
21. Если доступен браузер — проверить 375, 768, 1024 и 1440 px в обеих темах.
22. Если браузерного теста не было — не заявлять, что он выполнен.

# 37. Критерий готовности

Работа считается выполненной, если:

- создан `reviews.html`;
- страница связана с `clients.html`;
- использованы только реальные официальные письма;
- точное число писем проверено;

## Режим параллельной разработки — обязательно

Этот промпт выполняет **page-agent** в отдельной ветке/worktree. `main` — только базовая ветка.

### Владение файлами

Page-agent может создавать и менять только:
- целевую страницу этого промпта;
- уникальные assets, используемые только этой страницей;
- локальные стили этой страницы, если они необходимы.

Page-agent может читать, но **не должен изменять**:
- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- `docs/PHANTOM_SYNC_WORKFLOW.md`;
- общие CSS/JS;
- страницы других параллельных задач.

Если ниже по промпту требуется изменить общий файл, считать это **требованием для Integrator**. Не выполнять такую правку в page-ветке; перечислить её в финальном `Integration manifest`.
