# 5. Главное редакторское решение

**Не переносить старые статьи дословно.**

Причина:

часть старого контента содержит:

- неподтверждённые проценты эффективности;
- устаревшую продуктовую терминологию;
- слишком широкие compatibility claims;
- устаревшие версии Windows / Lync / АТС;
- риторику контроля сотрудников;
- юридически рискованные формулировки;
- обещания тестовой эксплуатации или коммерческих условий, которые могли измениться.

Новая `articles.html` должна быть **навигационным архивом**, а не способом повторно опубликовать устаревший маркетинговый текст.

Страница должна выглядеть как **knowledge/archive hub**, а не старый корпоративный блог.

Для опыта использовать `clients.html` и современные подтверждённые проекты.

---

# 34. Старые compatibility claims

Не переносить из старых статей как current:

- Microsoft Lync;
- универсальную поддержку всех типов телефонии;
- «любую CRM»;
- любые АТС;
- старые Windows UI claims.

Если статья их содержит — это ещё одна причина маркировать её архивной.

# 35. Что не делать

Не:

- менять production `mdis.ru`;
- копировать старые статьи целиком;
- создавать отдельные local article pages;
- создавать CMS;
- создавать scraper;
- показывать старые проценты как факт;
- повторять старые customer counts;
- обещать бесплатный тестовый период;
- выдавать старые compatibility claims за current;
- использовать риторику слежки за сотрудниками как современное позиционирование;
- писать, что система предотвращает ЧП;
- превращать articles hub в SEO-ферму;
- использовать выражение `реальное оборудование`.

# 37. Техническая проверка

После изменений:

1. Проверить `articles.html`.
2. Проверить один H1.
3. Проверить H1 → H2 → H3.
4. Проверить `noindex, nofollow`.
5. Проверить общий header.
6. Проверить общий footer.
7. Проверить light/dark.
8. Проверить связь `news.html ↔ articles.html`.
9. Проверить все архивные URL.
10. Проверить даты только там, где подтверждён год.
11. Проверить CRM article.
12. Проверить IP article.
13. Проверить energy article.
14. Проверить dispatcher article.
15. Проверить training article.
16. Проверить коммерческий архив.
17. Проверить все local `Актуальная информация` links.
18. Проверить отсутствие старых процентов в новом copy.
19. Проверить отсутствие бесплатных коммерческих обещаний.
20. Проверить отсутствие broken links.
21. Проверить отсутствие случайного перехода на `/`.
22. Проверить отсутствие horizontal overflow.
23. Если доступен браузер — проверить 375, 768, 1024 и 1440 px в обеих темах.
24. Если браузерного теста не было — не заявлять, что он выполнен.

# 38. Критерий готовности

Работа считается выполненной, если:

- создан `articles.html`;
- сохранён реальный раздел старого сайта `Статьи`;
- он отделён от `news.html`;
- старые статьи не скопированы дословно;
- статьи с устаревшими обещаниями маркированы как архивные;
- технические темы ведут прежде всего на актуальные локальные страницы;
- архивные оригиналы остаются доступны на `mdis.ru`;
- старые проценты и коммерческие обещания не перенесены;
- current compatibility не строится по старым статьям;
- production `mdis.ru` не затронут.

## Режим параллельной разработки — обязательно

Этот промпт выполняет **page-agent** в отдельной ветке/worktree. `main` — только базовая ветка.

### Владение файлами

Page-agent может создавать и менять только:
- целевую страницу этого промпта;
- уникальные assets, используемые только этой страницей;
- локальные стили этой страницы, если они необходимы.

Page-agent может читать, но **не должен изменять**:
- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- `docs/PHANTOM_SYNC_WORKFLOW.md`;
- общие CSS/JS;
- страницы других параллельных задач.

Если ниже по промпту требуется изменить общий файл, считать это **требованием для Integrator**. Не выполнять такую правку в page-ветке; перечислить её в финальном `Integration manifest`.

### Актуальность

Статические примеры общего header, `solutionPages`, порядка соседних страниц и других общих компонентов в этом промпте могли устареть. Не откатывать актуальный проект ради совпадения с примером. Текущее состояние базового `main` и правила `prompts/README.md` имеют приоритет для интеграции.

### Git и публикация

- Зафиксировать базовый commit SHA.
- Не коммитить напрямую в `main`.
- Не сливать свою ветку в `main`.
- Не публиковать на AEZA.
- Не менять production `mdis.ru`.

### Финальный отчёт

Помимо обычного отчёта промпта обязательно добавить `Integration manifest`: созданные page-owned файлы, необходимые изменения общих файлов, зависимости, выполненные и невыполненные проверки.
