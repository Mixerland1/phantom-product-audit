# 2. Главный принцип

Старый раздел:

https://mdis.ru/news/

содержит:

- новости;
- статьи;
- продуктовые релизы;
- совместимость;
- проекты;
- отраслевые публикации;
- старые маркетинговые статьи.

На новом сайте не нужно переносить десятки старых материалов.

Новая страница должна:

- показывать несколько **актуальных и содержательных** публикаций;
- кратко объяснять, почему они важны для продукта;
- вести на **полный официальный текст на `mdis.ru`**;
- давать переход в полный архив новостей;
- не создавать вторую независимую редакционную ленту, которая быстро разойдётся со старым сайтом.

# 6. Даты публикаций

Не угадывай год по позиции в ленте.

Для каждой карточки:

1. открой саму публикацию;
2. проверь доступную дату в HTML, metadata, structured data или официальной ленте;
3. если полный год подтверждён — показывай полную дату;
4. если официальный сайт показывает только день и месяц и год нельзя надёжно установить — не выдумывай год.

Не использовать дату индексации поисковиком.

# 16. Категории

Не создавать сложную систему фильтрации ради нескольких карточек.

- `Релиз`;
- `Новая функция`;

- `Проект`;
- `Документы`;
- `Разработка`.

Теги должны описывать фактический тип публикации.

Не создавать taxonomy/URL routes.

---

# 17. Не использовать автоматический scraper

Не создавать:

- parser `mdis.ru`;
- cron;
- RSS-parser;
- iframe старой страницы;
- серверный proxy;
- client-side fetch чужого HTML;
- CORS workaround.

Причины:

- новый сайт сейчас статический;
- структура старого сайта может меняться;
- парсер создаст ненужную эксплуатационную зависимость.

Карточки поддерживаются вручную в одном понятном месте.

---

# 18. Упростить дальнейшее обновление

Сделай структуру страницы так, чтобы редактор мог легко заменить/добавить карточку.

```html

</article>
```

с единообразной структурой.

Не зашивать карточки в сложный minified JavaScript.

Если используется JS для фильтрации — данные всё равно должны оставаться читаемыми в HTML.

# 22. Важное правило о новостях и продуктовых фактах

Новость может быть источником доказательства, но сама news-card не должна переписывать продуктовую страницу.

Например:

- ASR → подробности на `phantom-asr.html`;
- monitoring → `phantom-monitoring.html`;
- 5.5 → `phantom-cross.html`;
- Aviaton → `aviaton.html`.

News-hub отвечает:

```text
что произошло
```

Product page отвечает:

```text
что это за функция / продукт и как он работает
```

# 31. Визуальное оформление

Использовать:

- общий header;
- общий footer;
- текущую типографику;
- grid новостей;
- компактные category badges;
- даты;
- короткие аннотации;
- светлую и тёмную темы.

Предпочитать **text-first cards**.

Не использовать:

- generic newspaper stock;
- декоративные AI-картинки;
- случайные фотографии технологий;
- одинаковые абстрактные thumbnails;
- огромные изображения, если новости сами визуально слабые.

Если у конкретной официальной новости есть действительно полезный и качественный продуктовый визуал, допустимо скачать его локально и использовать.

## Режим параллельной разработки — обязательно

Этот промпт выполняет **page-agent** в отдельной ветке/worktree. `main` — только базовая ветка.

### Владение файлами

Page-agent может создавать и менять только:
- целевую страницу этого промпта;
- уникальные assets, используемые только этой страницей;
- локальные стили этой страницы, если они необходимы.

Page-agent может читать, но **не должен изменять**:
- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- `docs/PHANTOM_SYNC_WORKFLOW.md`;
- общие CSS/JS;
- страницы других параллельных задач.

Если ниже по промпту требуется изменить общий файл, считать это **требованием для Integrator**. Не выполнять такую правку в page-ветке; перечислить её в финальном `Integration manifest`.

### Актуальность

Статические примеры общего header, `solutionPages`, порядка соседних страниц и других общих компонентов в этом промпте могли устареть. Не откатывать актуальный проект ради совпадения с примером. Текущее состояние базового `main` и правила `prompts/README.md` имеют приоритет для интеграции.

### Git и публикация

- Зафиксировать базовый commit SHA.
- Не коммитить напрямую в `main`.
- Не сливать свою ветку в `main`.
- Не публиковать на AEZA.
- Не менять production `mdis.ru`.

### Финальный отчёт

Помимо обычного отчёта промпта обязательно добавить `Integration manifest`: созданные page-owned файлы, необходимые изменения общих файлов, зависимости, выполненные и невыполненные проверки.
