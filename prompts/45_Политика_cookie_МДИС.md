# Промпт для Codex: перенести локальную «Политику использования файлов cookie»

Ты работаешь в репозитории:

`Mixerland1/phantom-product-audit`

Базовая ветка: `main` (работа — в отдельной page-ветке).
Нужно **сразу создать и встроить в новый сайт локальную страницу политики использования файлов cookie** как перенос реальной страницы старого сайта.

Это юридический/комплаенс-документ. Не переписывай его в маркетинговом стиле и не добавляй новые правовые формулировки по своему усмотрению.

Сначала изучи актуальные файлы проекта и текущую официальную страницу МДИС, затем внеси изменения непосредственно в код.

---

# 1. Что создать

Создай новую корневую страницу:

`cookie-policy.html`

H1:

```text
Политика использования файлов cookie
```

Это **локальная юридическая страница**, отдельная от:

`privacy-policy.html`

Не объединять эти два документа.

---

# 2. Главный официальный источник

Используй текущую страницу:

https://mdis.ru/cookie-policy/

Перед реализацией обязательно открыть её заново и использовать **актуальную опубликованную редакцию на дату выполнения задачи**.

Не полагаться только на этот промпт, если официальный текст изменился.

---

# 3. Главный принцип

Для текста cookie-policy:

```text
не редактировать смысл без отдельного поручения владельца документа
```

Разрешено:

- перенести текст в новый HTML;
- адаптировать структуру;
- сделать headings/lists/tables;
- исправить технические HTML-артефакты;
- сделать mobile layout.

Нельзя самостоятельно:

- добавлять новые категории cookie;
- менять сроки хранения;
- менять сторонние сервисы;
- менять правовые основания;
- добавлять consent logic;
- добавлять GDPR/TCF;
- удалять упоминание Яндекс.Метрики;
- утверждать, что cookie нет, если фактический сайт их ставит.

# 5. Проверить фактический стек нового сайта

Это обязательная часть задачи.

Нужно понять:

- ставит ли сайт cookie вообще;
- подключена ли Яндекс.Метрика;
- есть ли другие analytics/marketing cookies;
- есть ли только технические storage-механизмы;
- используется ли localStorage для темы;
- используются ли session cookies;
- есть ли сторонние embeds.

Важно:

`localStorage` ≠ cookie.

Не описывать localStorage как cookie только потому, что это browser storage.

---

# 6. Если политика и фактический сайт расходятся

Примеры:

## Политика упоминает Яндекс.Метрику, а новый сайт её не подключает

Не переписывать policy самостоятельно.

В отчёте указать:

```text
Политика упоминает Яндекс.Метрику, фактический preview её не использует.
```

## Новый сайт подключает новый analytics/vendor, которого нет в policy

Не добавлять его «по ходу».

Указать mismatch в отчёте и оставить legal text без самовольного изменения.

## Сайт не ставит cookies вообще

Не удалять cookie-policy без решения владельца.

# 10. Не путать cookie и localStorage

В проекте `assets/site-header.js` может использовать:

```js
localStorage.setItem('mdis-theme', ...)
```

Это нужно учесть в техническом аудите, но:

- не называть это cookie;
- не добавлять в cookie-policy как cookie автоматически;
- при необходимости упомянуть в отчёте как client-side storage.

---

# 11. Яндекс.Метрика

Если официальная cookie-policy упоминает Яндекс.Метрику:

проверить:

- подключена ли она на новом сайте;
- есть ли script;
- есть ли counter id;
- ставятся ли analytics cookies;
- присутствует ли opt-out/consent logic.

Не выдумывать эти данные.

Если counter id есть в коде:

не публиковать его в тексте policy без необходимости.

---

# 12. Consent banner

Если на новом сайте есть cookie banner:

проверить:

- он реально появляется;
- текст соответствует фактическому использованию cookie;
- есть ссылка на `cookie-policy.html`;
- есть ссылка на `privacy-policy.html`, если предусмотрено;
- кнопки работают;
- выбор сохраняется;
- аналитика не загружается до согласия, если именно так требует реализованный сценарий.

Но не проектировать новый consent framework без отдельного требования, если сайт сейчас его не использует.

---

# 13. Если cookie banner отсутствует

Не создавать автоматически новый banner только потому, что существует cookie-policy.

Сначала определить фактическую необходимость по текущей архитектуре и project rules.

Если policy предполагает механизм согласия, а banner отсутствует:

указать mismatch в финальном отчёте.

# 41. Критерий готовности

Работа считается выполненной, если:

- создан `cookie-policy.html`;
- актуальная официальная редакция перенесена без самовольной смысловой правки;
- cookie-policy остаётся отдельной от privacy-policy;
- ссылки между двумя документами локальные;
- footer legal links локализованы;
- фактический analytics/cookie stack проверен;
- расхождения между policy и кодом перечислены в отчёте;
- localStorage не ошибочно назван cookie;
- новые vendors/сроки/categories не придуманы;
- production `mdis.ru` не затронут.

# 42. Формат отчёта после выполнения

После непосредственного внесения изменений коротко сообщи:

1. какие файлы созданы;
2. какие файлы изменены;
3. использована ли актуальная редакция `mdis.ru/cookie-policy/`;
4. были ли смысловые изменения текста — без отдельного поручения ответ должен быть `нет`;
5. какие analytics/cookie technologies реально используются новым сайтом;
6. используется ли Яндекс.Метрика;
7. используется ли localStorage и для чего;
8. есть ли cookie banner и соответствует ли он policy;
9. какие footer/privacy links локализованы;
10. какие mismatch между policy и фактическим кодом найдены;
11. какие проверки выполнены;
12. какие юридические несоответствия требуют решения владельца документа.

Не составляй новый план. Сразу реализуй страницу и необходимые точечные связи.

## Режим параллельной разработки — обязательно

Этот промпт выполняет **page-agent** в отдельной ветке/worktree. `main` — только базовая ветка.

### Владение файлами

Page-agent может создавать и менять только:
- целевую страницу этого промпта;
- уникальные assets, используемые только этой страницей;
- локальные стили этой страницы, если они необходимы.

Page-agent может читать, но **не должен изменять**:
- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- `docs/PHANTOM_SYNC_WORKFLOW.md`;
- общие CSS/JS;
- страницы других параллельных задач.

Если ниже по промпту требуется изменить общий файл, считать это **требованием для Integrator**. Не выполнять такую правку в page-ветке; перечислить её в финальном `Integration manifest`.

### Актуальность

Статические примеры общего header, `solutionPages`, порядка соседних страниц и других общих компонентов в этом промпте могли устареть. Не откатывать актуальный проект ради совпадения с примером. Текущее состояние базового `main` и правила `prompts/README.md` имеют приоритет для интеграции.

### Git и публикация

- Зафиксировать базовый commit SHA.
- Не коммитить напрямую в `main`.
- Не сливать свою ветку в `main`.
- Не публиковать на AEZA.
- Не менять production `mdis.ru`.

### Финальный отчёт

Помимо обычного отчёта промпта обязательно добавить `Integration manifest`: созданные page-owned файлы, необходимые изменения общих файлов, зависимости, выполненные и невыполненные проверки.
