# 5. Не создавать новые услуги

В рамках `services.html` не придумывать отдельные услуги:

- аудит инфраструктуры;
- консалтинг;
- интеграционный аудит;
- проектирование;
- SLA;
- круглосуточное сопровождение;
- внедрение «под ключ»;
- аренда оборудования;
- тестовый период;
- managed service;
- outsourcing.

Если они прямо не опубликованы как самостоятельные услуги — не выводить их отдельными карточками.

- обновление ПО через поддержку;
- контрактное послегарантийное обслуживание.

Эти условия **не переносить как актуальные коммерческие обязательства** без подтверждения.

Не писать на `services.html`:


Страница должна выглядеть как **service decision hub**.

Не использовать:

# 34. Приоритет визуальной иерархии

На первом экране пользователь должен сразу видеть три направления.

Не делать hero слишком высоким.

На desktop:

```text
[Персональные решения] [Модернизация] [Обучение]
```

можно показать уже в пределах первых 1–1.5 экранов.

На mobile:

карточки идут вертикально без горизонтального скролла.

---

# 35. Что не делать

Не:

- менять production `mdis.ru`;
- создавать четвёртую услугу;
- смешивать поддержку и услуги;
- смешивать продукт и услугу;
- копировать три service-pages целиком;
- переносить старые цены/скидки/обменные условия без проверки;
- переносить старые версии учебных программ как актуальные;
- обещать выезд/обучение на площадке без актуального подтверждения;
- обещать любую персональную доработку;
- обещать бесплатный тест;
- обещать бесплатный ремонт;
- использовать выражение `реальное оборудование`.

3. Проверить H1 → H2 → H3.
4. Проверить `noindex, nofollow`.
5. Проверить общий header.
6. Проверить общий footer.
7. Проверить светлую и тёмную темы.
8. Проверить три service-cards.
9. Проверить `personal-solutions.html`.
10. Проверить `modernization.html`.
11. Проверить `training.html`.
12. Проверить `support.html`.
13. Проверить `phantom-catalog.html`, если используется.
14. Проверить локальный `Услуги` в header.
15. Проверить Home.
16. Проверить Company.
17. Проверить footer.
18. Проверить mailto на `sales@mdis.ru`.
19. Проверить secondary support CTA.
20. Проверить отсутствие битых ссылок.
21. Проверить отсутствие случайного перехода на `/`.
22. Проверить отсутствие horizontal overflow.
23. Если доступен браузер — проверить 375, 768, 1024 и 1440 px в обеих темах.
24. Если браузерного теста не было — не заявлять, что он выполнен.

# 38. Критерий готовности

Работа считается выполненной, если:

- создан `services.html`;
- общий пункт `Услуги` стал локальным;
- на странице ровно три основные услуги старого раздела;
- каждая ведёт на актуальную локальную страницу;
- описание услуг не дублирует дочерние страницы;
- персональные решения, модернизация и обучение чётко разведены;
- техническая поддержка показана отдельно;
- стандартный выбор оборудования отправляет в каталог, а не автоматически в персональную разработку;
- старые коммерческие условия модернизации не выданы за актуальные без проверки;
- старые версии программ обучения не показаны как current;
- production `mdis.ru` не затронут.

## Режим параллельной разработки — обязательно

Этот промпт выполняет **page-agent** в отдельной ветке/worktree. `main` — только базовая ветка.

### Владение файлами

Page-agent может создавать и менять только:
- целевую страницу этого промпта;
- уникальные assets, используемые только этой страницей;
- локальные стили этой страницы, если они необходимы.

Page-agent может читать, но **не должен изменять**:
- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- `docs/PHANTOM_SYNC_WORKFLOW.md`;
- общие CSS/JS;
- страницы других параллельных задач.

Если ниже по промпту требуется изменить общий файл, считать это **требованием для Integrator**. Не выполнять такую правку в page-ветке; перечислить её в финальном `Integration manifest`.

### Актуальность

Статические примеры общего header, `solutionPages`, порядка соседних страниц и других общих компонентов в этом промпте могли устареть. Не откатывать актуальный проект ради совпадения с примером. Текущее состояние базового `main` и правила `prompts/README.md` имеют приоритет для интеграции.

### Git и публикация

- Зафиксировать базовый commit SHA.
- Не коммитить напрямую в `main`.
- Не сливать свою ветку в `main`.
- Не публиковать на AEZA.
- Не менять production `mdis.ru`.

### Финальный отчёт

Помимо обычного отчёта промпта обязательно добавить `Integration manifest`: созданные page-owned файлы, необходимые изменения общих файлов, зависимости, выполненные и невыполненные проверки.
