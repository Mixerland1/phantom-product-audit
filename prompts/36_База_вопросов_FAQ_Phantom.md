# 3. Почему нельзя копировать старый FAQ дословно

В старом FAQ есть полезная техническая информация, но также есть явно устаревшие или требующие проверки утверждения.

Примеры:

- Windows 2000;
- Windows XP;
- Windows Server 2003;
- Vista;
- старые модели Nortel / Siemens HiCom / NEC NEAX;
- утверждение `Phantom совместима с любыми существующими офисными АТС`;
- обещание бесплатной разработки интеграции за `1–2 недели`;
- бесплатная доставка и бесплатная пробная эксплуатация;
- гарантия `12 месяцев` как общий стандарт;
- юридическое объяснение о спецтехнике со ссылкой на постановление 1996 года;
- устаревшие накопители CD-RW / DVD-RW / стримеры / MODD;
- старые способы архивирования;
- старые алгоритмы/версии ПО без привязки к поколению продукта.

Новая база вопросов должна различать:

```text
актуальный подтверждённый ответ
```

и:

```text
исторический ответ старого FAQ, который нельзя переносить без проверки
```

# 5. Главный принцип

Каждый ответ в новом FAQ должен принадлежать к одному из трёх типов:

## A. Подтверждено актуальной документацией

Можно отвечать прямо.

## B. Зависит от версии / конфигурации

Нужно явно сказать:

```text
зависит от версии Phantom, платы, АТС, ОС или способа подключения
```

и дать ссылку на соответствующую страницу.

## C. Старый FAQ содержит ответ, который нельзя считать актуальным

Не повторять старую формулировку.

Использовать:

```text
Это условие необходимо уточнить у МДИС для текущей поставки / версии.
```

## Режим параллельной разработки — обязательно

Этот промпт выполняет **page-agent** в отдельной ветке/worktree. `main` — только базовая ветка.

### Владение файлами

Page-agent может создавать и менять только:
- целевую страницу этого промпта;
- уникальные assets, используемые только этой страницей;
- локальные стили этой страницы, если они необходимы.

Page-agent может читать, но **не должен изменять**:
- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- `docs/PHANTOM_SYNC_WORKFLOW.md`;
- общие CSS/JS;
- страницы других параллельных задач.

Если ниже по промпту требуется изменить общий файл, считать это **требованием для Integrator**. Не выполнять такую правку в page-ветке; перечислить её в финальном `Integration manifest`.

### Актуальность

Статические примеры общего header, `solutionPages`, порядка соседних страниц и других общих компонентов в этом промпте могли устареть. Не откатывать актуальный проект ради совпадения с примером. Текущее состояние базового `main` и правила `prompts/README.md` имеют приоритет для интеграции.

### Git и публикация

- Зафиксировать базовый commit SHA.
- Не коммитить напрямую в `main`.
- Не сливать свою ветку в `main`.
- Не публиковать на AEZA.
- Не менять production `mdis.ru`.

### Финальный отчёт

Помимо обычного отчёта промпта обязательно добавить `Integration manifest`: созданные page-owned файлы, необходимые изменения общих файлов, зависимости, выполненные и невыполненные проверки.
