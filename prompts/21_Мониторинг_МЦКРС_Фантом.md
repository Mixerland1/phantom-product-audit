## Режим параллельной разработки — обязательно

Этот промпт выполняет **page-agent** в отдельной ветке/worktree. `main` — только базовая ветка.

Page-agent может создавать и менять только:
- целевую страницу этого промпта;
- уникальные assets, используемые только этой страницей;
- локальные стили этой страницы, если они необходимы.

Page-agent может читать, но **не должен изменять**:
- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- `docs/PHANTOM_SYNC_WORKFLOW.md`;

- страницы других параллельных задач.

Если ниже по промпту требуется изменить общий файл, считать это **требованием для Integrator**. Не выполнять такую правку в page-ветке; перечислить её в финальном `Integration manifest`.

### Git и публикация

Помимо обычного отчёта промпта обязательно добавить `Integration manifest`: созданные page-owned файлы, необходимые изменения общих файлов, зависимости, выполненные и невыполненные проверки.

# 6. Самое важное ограничение: не придумывать 15 параметров

Официальная новость подтверждает:

```text
более 15 параметров
```

но сама новость не перечисляет их.

Поэтому действуй так:

## Если актуальная документация 5.5.2 содержит точный перечень параметров

Можно опубликовать **только этот подтверждённый перечень**.

## Если точного перечня нет

Не создавать список вроде:

- CPU;
- RAM;
- температура;
- RAID;
- свободное место;
- сеть;
- БД;
- лицензия;
- очередь;
- запись канала;

по собственной логике.

Вместо этого писать:

```text
МДИС сообщает о контроле работоспособности регистратора более чем по 15 параметрам. Детальный набор контролируемых показателей определяется версией программного обеспечения и конфигурацией системы.
```

Это обязательное правило.

# 7. Не смешивать мониторинг с архивом и записью

Мониторинг не является:

- движком записи;
- архивом;
- Web-интерфейсом работы с разговорами;
- системой резервного копирования;
- HA-кластером;
- SIEM;
- DLP.

Корректная логика:

```text
Phantom Logger / Server
        ↓
состояние компонентов
        ↓
Monitoring Agent
   ↙          ↘
Mon Web App   SNMP
                 ↓
        система мониторинга заказчика
```

# 15. Секция «Phantom Web App ≠ Mon Web App»

H2:

```text
Два Web-интерфейса — две разные задачи
```

Сравнительная таблица:

| | Phantom Web App | Phantom Mon Web App |
|---|---|---|
| Основная задача | работа с системой записи и архивом | эксплуатационный мониторинг |
| Записи | поиск, прослушивание и доступ в рамках прав | не основной сценарий |
| Пользователи | оператор / администратор Phantom | эксплуатационная служба |
| Состояние системы | не основной интерфейс мониторинга | основной сценарий |
| SNMP | не приписывать без документации | связан с Monitoring Agent |

Не делать вывод, что интерфейсы обязательно установлены на разных серверах.

# 26. Визуальное оформление

Страница должна выглядеть как **инфраструктурная техническая страница**, а не маркетинговый dashboard.

Использовать:

- общий header;
- общий footer;
- hero rhythm;
- архитектурные схемы;
- статусы/компоненты;
- аккуратную Web-panel metaphor только как схему;
- светлую и тёмную темы.

Не использовать:

- фальшивый Grafana;
- случайный NOC;
- зелёные `ALL SYSTEMS OK`;
- красивые, но выдуманные графики CPU/RAM;
- AI-generated dashboard;
- fake uptime 99.99%.

Если в официальной документации есть реальный скриншот `Phantom Mon Web App`, можно использовать его локально с корректным caption.

# 27. Главное меню

Не перегружать глобальный product dropdown ещё одним пунктом, если после предыдущих миграций там уже много элементов.

Предпочтительная навигация:

- `phantom-cross.html` → мониторинг;
- `phantom-catalog.html` → software / monitoring;
- `phantom-home.html` → monitoring proof-card;
- `modernization.html` → новые функции после обновления.

Если текущий `assets/site-header.js` имеет отдельную компактную техническую подкатегорию и новый пункт помещается без ухудшения desktop/mobile меню, допустимо добавить:

```js
monitoring: page(
  'phantom-monitoring.html',
  'phantom-monitoring.html',
  'phantom-monitoring.html'
)
```

и пункт:

```text
Мониторинг Phantom
```

Но **приоритет — не перегружать глобальное меню**.

Не создавать новый top-level пункт `Мониторинг`.

- escalation;
- incident tickets.

# 43. Критерий готовности

Работа считается выполненной, если:

- создан `phantom-monitoring.html`;
- monitoring показан как отдельный эксплуатационный модуль современной Linux-ветки;
- корректно разведены Phantom Web App и Phantom Mon Web App;
- объяснён Monitoring Agent;
- подтверждена интеграция по SNMP;
- сохранена формулировка `более 15 параметров` без выдуманного перечня;
- отдельно объяснены встроенный и внешний контуры мониторинга;
- monitoring не смешан с резервированием, архивом и поддержкой;
- нет выдуманных Grafana/Zabbix/API/alerting-функций;
- Cross, главная и связанные страницы ведут локально;
- production `mdis.ru` не затронут.
