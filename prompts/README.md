# Prompts — правила параллельной разработки Phantom

Эта папка содержит исполнимые промпты для создания и переноса страниц сайта Phantom / МДИС.

Главная цель правил ниже — позволить нескольким page-agent работать параллельно без взаимного затирания изменений в общих компонентах сайта.

## 1. Роли

### Page-agent

Page-agent создаёт **одну целевую страницу** по одному промпту в отдельной ветке/worktree.

Он отвечает за:

- целевой HTML своей страницы;
- уникальные изображения и другие assets, относящиеся только к этой странице;
- локальные стили внутри своей страницы, если без них нельзя обойтись;
- статическую проверку своей страницы;
- финальный список интеграционных изменений, которые понадобятся после принятия страницы.

Page-agent **не интегрирует** свою страницу в общие компоненты сайта.

### Integrator

Integrator работает после принятия page-веток и является единственным владельцем общих файлов.

Только integrator меняет:

- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- общие CSS/JS;
- общие массивы маршрутов, меню и циклической навигации;
- cache-bust версии общих ресурсов на других страницах.

Integrator объединяет принятые страницы, обновляет общую навигацию одним согласованным изменением и проверяет, что ни одна страница не затёрла изменения другой.

### QA / publisher

После интеграции выполняется единый QA-проход. Публикация на AEZA выполняется только после него и только отдельным действием.

## 2. Запрещённые для page-agent общие файлы

Page-agent может читать, но не должен изменять:

- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- `docs/PHANTOM_SYNC_WORKFLOW.md`;
- общие CSS/JS, которые уже используются несколькими страницами;
- чужие целевые страницы, над которыми параллельно работают другие агенты.

Если исходный промпт требует изменить один из этих файлов, требование **не удаляется**, но считается пунктом для Integrator. Page-agent записывает его в финальном отчёте в разделе `Integration manifest`.

Исключение возможно только если пользователь явно назначил текущего агента Integrator.

## 3. Ветки и базовый SHA

- Не работать page-agent напрямую в `main`.
- Для каждой страницы использовать отдельную ветку/worktree, например:
  - `page/atom-energy`;
  - `page/stantsiya-zapisi`;
  - `page/industrial`;
  - `page/government`;
  - `page/financial`;
  - `page/commercial`.
- Все агенты одной параллельной волны должны стартовать от согласованного состояния `main`.
- В отчёте page-agent указывает базовый commit SHA, от которого начал работу.
- Если в самом промпте написано `Ветка: main`, это означает **базовую ветку проекта**, а не разрешение коммитить непосредственно в `main`.

## 4. Приоритет актуального проекта над статическим текстом промпта

Промпт может содержать снимок навигации или структуры на момент его подготовки.

Поэтому:

1. Page-agent читает актуальные `AGENTS.md`, эталонные страницы и общие файлы из своей базовой версии.
2. Не откатывает более новые решения проекта ради совпадения со старым фрагментом кода в промпте.
3. Не переписывает общий `solutionPages`, header или главную страницу.
4. Если ожидаемое состояние из промпта расходится с актуальным проектом, фиксирует расхождение в `Integration manifest`.
5. Содержательные требования страницы, источники, ограничения формулировок и технические факты сохраняются, если они не были отдельно отменены пользователем.

## 5. Что page-agent может менять

Разрешено:

- создать целевой `*.html`;
- создать уникальный asset страницы в `assets/backgrounds/`, `assets/products/` или другой существующей подходящей папке;
- добавить локальный CSS в саму страницу, если это соответствует текущему шаблону;
- изменить созданный им же уникальный asset.

Нельзя без роли Integrator:

- добавлять маршрут в общий header;
- менять порядок отраслей;
- менять циклический switcher;
- менять ссылки на главной;
- менять cache-bust на чужих страницах;
- править общий footer/header/CSS/JS;
- публиковать на AEZA;
- сливать ветку в `main`.

## 6. Integration manifest — обязательный финальный блок page-agent

В конце работы page-agent должен вернуть:

```text
Integration manifest

Target page:
- <имя созданной страницы>

Base commit:
- <SHA>

Created/changed page-owned files:
- ...

Shared changes required from Integrator:
- assets/site-header.js: ...
- assets/footer-next.js: ...
- phantom-home.html: ...
- shared CSS/JS: ...
- other: ...

Dependencies:
- ...

Checks completed:
- ...

Checks not completed:
- ...
```

Если общих изменений не требуется, написать `none`, а не менять общий файл «на всякий случай».

## 7. Рекомендуемая схема текущей серии

Безопасная последовательность:

1. Создать и принять `atom-energy.html` как первый дополнительный отраслевой эталон.
2. После этого параллельно запускать:
   - `stantsiya-zapisi.html`;
   - `industrial.html`;
   - `government.html`;
   - `financial.html`;
   - `commercial.html`.
3. После готовности веток один Integrator:
   - переносит/сливает принятые page-owned файлы;
   - один раз обновляет header;
   - один раз обновляет `solutionPages`;
   - один раз переводит нужные ссылки `phantom-home.html` на локальные страницы;
   - обновляет cache-bust только там, где это действительно нужно.
4. Затем единый QA.
5. Затем отдельная публикация через действующий Phantom Sync workflow.

Практический предел — 3–5 параллельных page-agent. Количество ограничивает не Git, а удобство проверки результатов и разрешения содержательных расхождений.

## 8. QA после интеграции

Перед публикацией проверить как минимум:

- один H1 на каждой странице;
- H1 → H2 → H3;
- `noindex, nofollow`;
- единый header/footer;
- светлую и тёмную темы;
- отраслевой цикл в порядке меню;
- локальные ссылки на уже перенесённые страницы;
- отсутствие случайных ссылок на корень `/`;
- отсутствие конфликтов общих CSS/JS;
- отсутствие горизонтального overflow;
- форму `mailto:`, если она есть;
- 375, 768, 1024 и 1440 px в обеих темах, если доступен браузерный рендер.

Не заявлять браузерную проверку, если она фактически не выполнялась.

## 9. Как обрабатывать новые промпты, добавляемые в эту папку

Перед сохранением каждого нового промпта:

1. Сохранить его содержательные требования, источники и ограничения.
2. Заменить смысл `Ветка: main` на «базовая ветка main».
3. Вставить стандартный блок **«Режим параллельной разработки — обязательно»** из раздела ниже.
4. Найти все требования менять общие файлы и оставить их в промпте как **интеграционные требования**, но запретить page-agent выполнять их непосредственно.
5. Проверить, нет ли в промпте устаревшего снимка порядка навигации; такой снимок не должен иметь приоритет над актуальным `main`.
6. Не менять факты и редакционные ограничения промпта без отдельного основания.
7. Не превращать промпт в новый аудит: задача по-прежнему должна оставаться исполнимой.
8. Добавить промпт в список файлов в этом README.

## 10. Канонический блок для каждого параллельного промпта

Ниже приведён блок, который должен присутствовать в каждом page-промпте этой папки:

```markdown
## Режим параллельной разработки — обязательно

Этот промпт выполняет **page-agent** в отдельной ветке/worktree. `main` — только базовая ветка.

### Владение файлами

Page-agent может создавать и менять только:
- целевую страницу этого промпта;
- уникальные assets, используемые только этой страницей;
- локальные стили этой страницы, если они необходимы.

Page-agent может читать, но **не должен изменять**:
- `assets/site-header.js`;
- `assets/footer-next.js`;
- `phantom-home.html`;
- `AGENTS.md`;
- `docs/PHANTOM_SYNC_WORKFLOW.md`;
- общие CSS/JS;
- страницы других параллельных задач.

Если ниже по промпту требуется изменить общий файл, считать это **требованием для Integrator**. Не выполнять такую правку в page-ветке; перечислить её в финальном `Integration manifest`.

### Актуальность

Статические примеры общего header, `solutionPages`, порядка соседних страниц и других общих компонентов в этом промпте могли устареть. Не откатывать актуальный проект ради совпадения с примером. Текущее состояние базового `main` и правила `prompts/README.md` имеют приоритет для интеграции.

### Git и публикация

- Зафиксировать базовый commit SHA.
- Не коммитить напрямую в `main`.
- Не сливать свою ветку в `main`.
- Не публиковать на AEZA.
- Не менять production `mdis.ru`.

### Финальный отчёт

Помимо обычного отчёта промпта обязательно добавить `Integration manifest`: созданные page-owned файлы, необходимые изменения общих файлов, зависимости, выполненные и невыполненные проверки.
```

## 12. Рекомендуемая последовательность для промптов 07–18

Чтобы не создавать лишние внешние ссылки и не заставлять page-agent видеть незамёрженные изменения других веток, использовать следующую последовательность:

1. Первая параллельная волна:
   - `07_Автосалоны.md`;
   - `08_Phantom_MICRO.md`;
   - `09_Платы_Phantom_Ph-200_Ph-500_Ph-600.md`;
   - `10_Phantom_Active.md`.
2. После приёмки и интеграции `phantom-active.html` запускать `11_Запись_IP-телефонии.md`, чтобы страница IP-записи могла сразу использовать локальную ссылку на Phantom Active. Если №11 всё же запускается параллельно с №10, page-agent не должен видеть чужую branch; необходимость заменить внешнюю ссылку на локальную фиксируется в `Integration manifest`.
3. `12_Каталог_линейка_Phantom.md` запускать после интеграции доступных продуктовых и технологических страниц. Каталог является хабом и должен строить перелинковку по фактическому состоянию актуального `main`, а не по предположению, что соседние страницы уже созданы.
4. После интеграции №12 запускать `13_Схемы_подключения_МЦКРС_Фантом.md`. Эта страница должна видеть локальные каталог, IP-запись, платы и Phantom Active, если они уже приняты.
5. Следующую сервисную волну можно запускать параллельно:
   - `14_Персональные_решения.md`;
   - `15_Комплексная_модернизация_Phantom.md`;
   - `16_Обучение_по_Phantom.md`.
   Эти страницы могут ссылаться друг на друга только после интеграции; если соседняя сервисная страница ещё в отдельной branch, page-agent фиксирует будущую локальную ссылку в `Integration manifest`, но не читает и не меняет чужую ветку.
6. После интеграции №13 запускать `17_Запись_телефонных_переговоров.md`, потому что она использует каталог, IP-запись, схемы подключения, платы и продуктовые страницы как связанные разделы.
7. `18_Запись_диспетчерских_переговоров.md` запускать после интеграции №17 и уже принятых отраслевых/диспетчерских страниц. Она должна строить связи по фактическому состоянию `main`, особенно с `telephone-recording.html`, `stantsiya-zapisi.html`, `aviaton.html`, `atom-energy.html` и `electroenergetika.html`.
8. После каждой волны один Integrator выполняет общие изменения header/footer/home/shared CSS/JS и cache-bust, затем единый QA.
